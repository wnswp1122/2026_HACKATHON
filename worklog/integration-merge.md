## 계획 검증

- 수집·전송, SaaS 데이터·AI, 프론트를 나눠 코드를 독립 검토한다. 단순 파일 충돌과 실제 계약 불일치를 구분한다.
- 공통 DB와 설정은 SaaS core가 소유한다. data/AI의 import, 테이블·열, 요청·응답 모델이 일치해야 한다. 스키마는 서버 기동 전에 명시적으로 적용한다.
- 이벤트와 센서 상태는 독립 전송 경로다. `source=sample/live`, 수신 시각·발생 시각, 정책 요청 행동·실제 결과를 합치지 않는다.
- 프론트는 실제 API 응답으로 조회하고, 스냅샷 허용 필드와 고정 PNG가 AI 요청까지 유지되는지 확인한다.
- 자동 병합 결과에 충돌이 있으면 해당 소유 모듈과 계약을 기준으로 해결한다. 일괄 ours/theirs 처리나 기존 작업 공간 초기화는 하지 않는다.

## 실행과 머지 조건

1. 위 순서로 통합 브랜치에 merge commit을 남겨 기능 브랜치 이력을 보존한다.
2. 의존성·프론트 타입/빌드, Python import, 전체 모듈 로드, DB 스키마 적용을 확인한다.
3. 별도 통합 DB에 실제 Tetragon 기록을 sample로 전송하고 인증 실패·중복 ACK·조회·리플레이·스냅샷을 확인한다. Linux에서 새로 관찰한 이벤트를 live로 전송하는 흐름도 확인한다.
4. 실제 백엔드에 연결한 브라우저에서 5개 화면과 PNG 업로드를 확인한다. AI 외부 응답을 모의하면 실제 제공자 호출과 분명히 구분하며, 운영 키 없음을 숨기지 않는다.
5. 확인 중 발견한 연결 문제만 최소 수정하고 관련 확인을 반복한다. 실행 방법과 검증·미검증 범위를 이 기록 및 PR에 남긴다.
6. 고정한 모든 HEAD의 포함 여부, 원격 master 변화, 충돌·리뷰·필수 검사 상태를 확인하고 통합 PR을 머지한다. 기능 PR 상태도 다시 조회한다.
7. 후속 사용자 요청에 따라 머지 후 다시 검증하고 프론트·필수 서버를 켜둔다. 실제 화면을 열고 접속 주소를 전달한다. 코드·DB 볼륨·기존 워크트리는 보존한다.

## 실행 결과

### 코드·계획 확인

- 수집·전송, 백엔드, 프론트를 독립 검토했다. 공통 스키마·import·라우터·요청/응답 계약이 일치했으며 8개 대상 커밋을 충돌 없이 merge commit으로 조립했다.
- 실제 PostgreSQL 17, Python 3.12, 통합 코드의 네 FastAPI 모듈로 검증했다. 프론트 의존성 설치·타입 검사·프로덕션 빌드가 통과했다. 624KB 번들 경고는 남아 있다.
- [시나리오 검증 스크립트 계획](../docs/scenario-verification-plan.md)을 병렬 작성하고 현재 CLI·HTTP 계약, 링크와 기대 결과를 재확인했다. 반복 실행기 자체는 아직 구현하지 않았다.

### 실제 통합 확인

- 별도 `hack-integration-db`에 기존 Tetragon 공개 기록 29건을 `source=sample`로 저장했다. EXEC 10, EXIT 10, FILE_ACCESS 6, NETWORK 3이며 새 live 수집으로 표현하지 않는다.
- HTTP 검증 47개 조건 통과: 네 모듈 로드, 이벤트·상태 저장, 동일 ID 중복 ACK, 내용 변경 409, 인증 누락 401, 허용 외 서버 403, 5종 조회와 준비 점검, 리플레이·스냅샷 생성/재조회, PNG 없는 분석 거부.
- 실제 SaaS에 연결한 브라우저에서 5개 화면, sample/NETWORK 필터, 원본 상세, 29건 리플레이 생성·이동·재생·새로고침 복원을 확인했다. API 모의 대체 없이 실행했고 브라우저 예외는 0건이었다.
- 브라우저에서 만든 안전 PNG 188,281바이트가 업로드됐고 SHA-256이 서버 저장값과 일치했다. 실제 서버의 AI 미설정 503 및 스냅샷 복원을 확인했다.
- 별도 프로세스에서 외부 AI HTTP만 모의 대체하여 같은 실제 DB·브라우저 PNG·안전 스냅샷 → 분석 저장 → 실제 HTTP GET 복원을 확인했다. 같은 ID 재요청은 기존 결과를 반환하고 외부 모의 호출은 1회였다. 실제 모델 호출은 하지 않았다.

### 발견한 통합 문제와 수정

공유 Linux VM에 SaaS PostgreSQL도 두면 수신 요청마다 생성·종료되는 DB 프로세스를 Tetragon이 다시 수집하는 순환이 발생했다. 검증 중 PostgreSQL 종료 이벤트 2,750건을 확인했고 전송기 파일 회전 종료도 발생했다. 이벤트 전송을 중지하고 해당 실행의 격리 DB 데이터만 정리했다. 원본 로그·기존 게시판/DB 볼륨은 보존했다.

`runtime.py start`에 선택적 `TETRAGON_EXPORT_DEMO_ONLY=1`을 추가했다. 현재 게시판 컨테이너 ID에 대한 Tetragon native JSON export 필터를 사용한다. 미설정/0은 기존 전체 export이고, 잘못된 값 또는 기존 컨테이너와 필터 불일치는 실패한다. 일반 고객 서버 수집을 이 시연용 제한으로 바꾸지 않는다. 상세 실행과 공식 근거는 [Tetragon 안내](../tetragon/README.md#게시판과-saas-db를-같은-vm에서-검증할-때)에 있다.

수정 후 새 live 12건(EXEC 4, EXIT 4, FILE_ACCESS 2, NETWORK 2)이 전달됐고 8초 뒤에도 12건, PostgreSQL 이벤트 0건이었다. 잘못된 설정·기존 컨테이너 옵션 불일치 거부 및 같은 옵션 재시작도 확인했다. 이후 enforce probe는 exit 137·원본 SIGKILL·READ_OK 없음, 게시판 health 200을 확인했다. observe 복구 후 probe READ_OK·exit 0·health 200, 최종 observe/network 활성·enforce 해제를 확인했다. 해당 구간 live 16건 중 정책 행동 SIGKILL 2건은 `attention`, `outcome=unknown`으로 저장됐다. 실측 프로세스 종료와 대시보드의 보수적인 결과 표시를 구분한다.

### 직접 확인 환경

- 프론트: `http://127.0.0.1:5173/overview`, 실제 SaaS: `http://127.0.0.1:18010`, 게시판: `http://127.0.0.1:8081/docs`.
- 프론트는 `VITE_API_PROXY_TARGET=http://127.0.0.1:18010`으로 연결한다. `integration-sample`의 sample 기록과 `integration-live`의 새 관찰을 구분해 선택한다.
- DB는 전용 Lima VM의 `hack-integration-db`와 SSH 15434 터널을 사용한다. 백엔드는 `backend/.env.example`의 필수 설정을 적용하고 `python db.py` 후 시작한다. 위치/AI 설정은 같은 예제에 통합했다.
- 원시 실행 자료·화면 캡처는 통합 작업 공간의 Git 제외 `.local/`에 있다. 저장소에는 정제한 결과만 기록한다.

### 남은 범위

실제 AI 제공자 호출, 자동 GeoIP, 운영 인증·배포·부하·영속 전송 큐는 확인하거나 구현한 범위가 아니다. 현재 네트워크 정책은 로컬 전용 probe를 관찰하므로 실제 해외 지구본 점이 생기지 않는다. 위치 미설정 UI를 확인했고 좌표 배치는 별도 위치 설정 시 확인해야 한다. Tetragon v1.8.0의 개별 센서 조회 미지원은 준비 상태 `unknown`으로 표시하는 것이 정상이다.
