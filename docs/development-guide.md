# 개발 시작 안내

이 문서는 팀원과 작업을 맡은 AI가 **현재 목표, 담당 범위, 연결 지점, 검증 방법**을 이해하기 위한 공통 출발점이다. 실제 코드와 실행 결과가 이 문서의 예시와 다르면 현재 상태를 확인하고 팀과 계약을 맞춘다.

## 1. 만들 것

로컬 Linux 환경의 시연 서버에서 Tetragon으로 활동을 관찰한다. 사람이 미리 준비한 정책에 따라 지원되는 대응을 수행하고, 이벤트를 우리 서버로 보내 대시보드의 경고와 AI 조사 안내를 보여준다.

```text
시연용 서버 → Tetragon 관찰·대응 → 전송 모듈 → 백엔드 → 대시보드·알림
                                                      └→ AI 조사 안내
```

- **필수:** 실제 Tetragon 이벤트 수신, 대시보드 표시, 화면 내 새 경고, 대응 결과의 별도 확인, 선택 이벤트의 AI 분석.
- **제외:** AI의 정책 YAML 수정, 정책 자동 배포, AI에 의한 실시간 차단, 취약점 자동 수정, 실제 고객 연결, 외부 메시지 발송.
- **의미:** 이벤트는 관찰된 사실이고, 경고는 정책 또는 시연 조건에 맞는 활동이다. 어느 쪽도 공격이나 취약점을 확정하지 않는다.
- **중요:** `SIGKILL`은 프로세스 종료이며 작업이 실행되지 않았다는 증거가 아니다. 작업 거부를 시연한다면 사용 가능한 정책·훅을 확인하고 실제 작업 결과를 검증한다.

## 2. 현재 상태와 환경

저장소에는 폴더와 설명, Python 의존성 설정만 있다. **애플리케이션 코드, Tetragon 정책, 설치·실행 스크립트, AI 연동은 아직 없다.** 동작하거나 검증된 것으로 가정하지 않는다.

- 백엔드: Python 3.12, FastAPI, Uvicorn, HTTPX. `backend/requirements.txt` 사용.
- 전송 모듈: Python. 화면: HTML·CSS·JavaScript로 시작하고 별도 빌드 도구를 요구하지 않는다.
- 데이터 저장: 우선 프로세스 메모리. 재시작하면 이벤트가 사라진다.
- Tetragon: 호환 Linux 커널, 실행 권한과 별도 설치가 필요하다. macOS Docker Desktop에서는 Linux VM의 활동을 관찰한다. 해당 VM에서 정책과 드라이버가 작동하는지는 아직 확인되지 않았다.
- AI 제공자·모델과 인증 변수, Tetragon 버전, 시연 행동 및 정책은 미정이다. 임의의 비밀키를 작성하지 않는다.

저장소 루트에서 환경을 준비한다.

```sh
python3 -m venv .venv
. .venv/bin/activate
python -m pip install -r backend/requirements.txt
cp .env.example .env
```

`.env`는 Git에 올리지 않는다. 환경변수 예시를 추가하되 실제 비밀값은 넣지 않는다. 실행 코드를 만들기 전에는 애플리케이션 실행 명령이 없다. 각 담당자는 구현 후 실행 방법과 실제 확인 결과를 해당 README에 추가한다.

## 3. 담당 범위

| 경로 | 목표 | 연결 대상 |
|---|---|---|
| `demo/` | 격리된 서버·파일과 반복 가능한 시연 행동 | Tetragon 담당자 |
| `tetragon/` | 관찰 및 대응 정책을 준비하고 실제 결과 검증 | 이벤트 원본·재현 방법을 전송 담당자에게 공유 |
| `event-forwarder/` | 실제 Tetragon 이벤트를 읽어 백엔드로 HTTP 전송 | `POST /api/events` |
| `backend/src/events/` | 이벤트 수신·정리·저장·조회·경고 분류 | 전송 모듈과 화면 |
| `backend/src/analysis/` | 이벤트와 서버 맥락으로 AI 조사 안내 생성 | AI 제공자와 화면 |
| `frontend/src/events/` | 목록·상세·화면 알림 | 백엔드 이벤트 API |
| `frontend/src/analysis/` | AI 분석 요청·결과·실패 표시 | 백엔드 분석 API |

각 폴더의 README에 세부 목표와 완료 조건이 있다. 코드 분리는 책임을 알아볼 수 있는 최소 수준으로 하고, 인터페이스나 공통 계층을 미리 늘리지 않는다.

## 4. 작업 순서와 연결 계약

1. **Tetragon·시연:** Linux에서 기본 이벤트를 확인하고, 시연 행동 하나와 대응 목표를 선택한다. 정책 전후의 실제 행동, 원본 JSON, 실행 환경과 재현 방법을 공유한다.
2. **백엔드·전송:** 예시 데이터로 수신과 목록 조회를 연결한 후 실제 Tetragon JSON으로 확인한다. JSON 파일 또는 gRPC 중 검증된 한 방식을 택한다.
3. **화면:** 예시 데이터로 목록·상세·알림을 준비하고 백엔드에 연결한다. 새 경고 알림은 화면 내 표시이며 열린 화면에서만 동작한다.
4. **AI:** 이벤트 상세에서 사용자가 요청할 때만 분석한다. 서버 설명과 실제 관찰 정보만 보내고, 사실·가능성·확인 사항을 구분한다.
5. **통합:** 행동 발생 → 실제 이벤트 → 화면 경고 → AI 결과와 실제 대응 확인을 처음부터 실행한다.

백엔드 API는 아래 경로를 기준으로 작업한다. 페이로드와 오류 형식은 **초안**이며 실제 Tetragon JSON을 확인한 뒤 백엔드·전송·화면 담당자가 합의해 함께 고친다. 합의 전 서로 다른 확정 계약인 것처럼 구현하지 않는다.

| 메서드·경로 | 역할 |
|---|---|
| `POST /api/events` | 이벤트 수신 |
| `GET /api/events` | 최신 이벤트 목록 |
| `GET /api/events/{id}` | 이벤트 상세 |
| `POST /api/events/{id}/analysis` | 선택한 이벤트 분석 |

공통 내부 필드 초안은 `docs/runtime-security-design.md`를 따른다. 발생 시각, 프로세스, 정책명, 대상, 대응 결과가 실제 데이터에 없으면 미상으로 다룬다. **원본 JSON은 Tetragon 형식 그대로 보관하되** 민감한 인자 등은 AI에 보내기 전에 범위를 정한다. AI 실패가 이벤트 수신·조회 실패로 이어지면 안 된다.

## 5. 각 팀원이 AI에게 요청하는 방법

작업을 시작할 때 아래 문장을 담당 범위에 맞게 전달한다.

> `docs/development-guide.md`, `docs/runtime-security-design.md`와 담당 폴더의 README를 읽고 [담당 컴포넌트]를 구현해 줘. 다른 팀의 미완성 부분은 계약에 맞춰 연결하고, 실제 확인한 동작과 아직 확인하지 못한 부분을 구분해서 알려줘.

AI는 작업 전 저장소의 `AGENTS.md`, 현재 코드·설정·변경 상태를 확인하고 다른 팀의 작업을 보존한다. 실제 원본 이벤트, API 계약, 정책 지원 또는 AI 제공자가 미정이면 임의로 검증 결과를 만들지 않는다. 연동을 막지 않는 범위에서 예시 데이터를 사용하되, 실제 이벤트와 구분한다. 공통 계약을 변경해야 하면 소비자에게 공유하고 문서를 함께 갱신한다.

## 6. 완료 확인

- [ ] Linux에서 시연 행동과 Tetragon 이벤트를 실제로 확인했다.
- [ ] 정책 적용 전후의 프로세스 상태 또는 작업 결과를 독립적으로 확인했다.
- [ ] 실제 이벤트가 백엔드에 도착하고 대시보드에 표시된다.
- [ ] 열린 대시보드에서 새 경고가 표시된다.
- [ ] 선택한 이벤트의 AI 결과가 표시되며 실패 시 조회 기능은 유지된다.
- [ ] 실행 방법, 환경변수 이름, 실제 확인한 범위와 남은 문제를 README에 기록했다.

경고 전달과 대응은 독립된 흐름이다. 경고 수신만으로 차단 성공을 표시하지 않는다. 실행되지 않은 기능이나 실제로 검사하지 않은 보안 효과는 완료로 보고하지 않는다.
