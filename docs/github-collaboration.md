# GitHub 협업 규칙

## 기본 원칙

1. **이슈 없이 PR로 작업을 기록한다.** 별도 이슈 생성이나 이슈 번호 연결을 요구하지 않는다.
2. **로컬에서 검증한 뒤 푸시한다.** 변경한 기능을 직접 실행하거나 변경에 맞는 검사를 수행한다.
3. **의미 있는 작업 단위로 커밋한다.** 기능 구현, 오류 수정, 문서 수정처럼 설명 가능한 단위로 묶는다.
4. **기능별로 PR을 만든다.** 서로 독립적인 기능을 한 PR에 섞지 않는다.
5. **머지도 검증 후 진행한다.** PR의 변경 내용과 검증 결과를 확인하고, 통합 영향이 있으면 최신 대상 브랜치와 함께 동작을 확인한다.

## 작업 순서

### 1. 기능 브랜치에서 시작

대상 브랜치는 현재 저장소의 `master`다. 개인 변경이 있는 상태에서 다른 브랜치로 무리하게 이동하지 않는다. 기존 변경을 보존한 뒤 기능 브랜치 또는 별도 작업 공간을 사용한다.

깨끗한 작업 공간에서 새 작업을 시작하는 예:

```sh
git switch master
git pull --ff-only origin master
git switch -c feat/event-ingest
```

브랜치 이름 예: `feat/event-ingest`, `feat/dashboard`, `fix/event-time`, `docs/setup-guide`. 브랜치 이름은 예시이며 특정 이름을 강제하지 않는다.

### 2. 단위별 커밋

- 한 커밋의 목적을 한 문장으로 설명할 수 있게 나눈다.
- 여러 파일이 하나의 기능을 함께 구성하면 같은 커밋에 포함할 수 있다.
- 독립적인 리팩터링이나 다른 사람의 변경을 끼워 넣지 않는다.
- 키, `.env`, 가상환경, 실제 고객 데이터는 커밋하지 않는다.

예:

```text
feat: Tetragon 이벤트 수신 및 메모리 저장
feat: 이벤트 목록 조회 API 추가
fix: 정책명이 없는 이벤트의 처리 오류 수정
docs: 이벤트 수신 API 수동 확인 방법 추가
```

### 3. 로컬 검증 후 푸시

푸시할 커밋에 대해 관련 동작을 확인한다. 검증 후 코드를 변경했다면 영향을 받는 확인을 다시 수행한다. 자동 테스트나 CI 추가는 필수가 아니다.

| 변경 | 최소 확인 예 |
|---|---|
| 백엔드 | 서버 기동, 변경한 API 성공·실패 응답 |
| 화면 | 브라우저에서 관련 동작과 오류 표시 |
| 이벤트 전송 | 입력 JSON이 백엔드에 도착, 전송 실패 처리 |
| Tetragon 정책 | 정책 로드, 대상 행동 재현, 실제 프로세스·작업 결과 |
| 문서만 | 실제 파일·계약과 일치, 상대 링크와 명령 전제 확인 |

```sh
git diff --check
git status --short
# 변경에 맞는 실행 확인 후
# 필요한 파일을 지정해 커밋하고 원격에 푸시한다.
git push -u origin feat/event-ingest
```

실제 환경에서 확인할 수 없는 부분은 PR에 명시한다. 예시 JSON으로 API를 확인한 것을 실제 Tetragon 연동 확인으로 기록하지 않는다. 핵심 기능의 검증이 남았으면 PR을 Draft로 두고 머지하지 않는다.

### 4. 기능별 PR

한 PR은 하나의 기능 또는 독립적인 수정 목적을 가진다. PR 본문만 읽어도 무엇을 바꿨고 어떻게 확인했는지 알 수 있어야 한다. 다른 PR의 코드가 필요하면 선행 PR을 링크한다.

아래 형식을 복사해 쓴다. 별도 이슈는 필요 없다.

```markdown
## 변경
- 해결할 문제와 변경 후 동작

## 중요한 판단·연결 지점
- 변경한 API/이벤트 형식, 영향받는 컴포넌트 또는 없음
- 선행 PR이 있으면 링크

## 로컬 검증
- 실행한 환경·명령/조작과 실제 결과
- 사용한 데이터가 실제 이벤트인지 예시인지

## 남은 확인
- 미검증 범위 또는 없음
```

### 5. 검증 후 머지

- 작성자 또는 팀원이 PR diff, 공개 계약 변경, 로컬 검증 기록을 확인한다.
- 대상 브랜치 변경이 해당 기능에 영향을 주거나 충돌을 해결했다면 최신 코드와 합친 상태에서 다시 확인한다.
- 통합 흐름이 바뀌면 [수동 확인 절차](manual-verification.md)의 관련 시나리오를 실행한다.
- 문제가 남아 있거나 핵심 검증이 불가능하면 머지를 보류하고 PR에 남긴다.
- 머지 방식은 팀이 선택한다. CI가 없다는 이유로 검증 없이 머지하지 않는다.

푸시·머지 권한은 현재 작업에서 팀 또는 사용자가 허용한 범위를 따른다. 이 문서는 AI에 모든 후속 작업의 푸시·머지를 일괄 승인하는 문서가 아니다.
