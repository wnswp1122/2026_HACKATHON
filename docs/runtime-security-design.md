# Tetragon 기반 보안 모니터링과 대응 설계

## 목표와 범위

로컬 Linux 환경에서 Tetragon으로 서버 활동을 관찰하고, 미리 정한 정책에 해당하는 행동에 대응한다. 우리 서비스는 이벤트를 수집해 대시보드와 화면 알림으로 보여주고 AI 조사 안내를 제공한다.

5시간 안에 개발하는 것을 기준으로 **단일 시연 행동에 대한 실제 이벤트 수집과 대응 결과 확인**을 우선한다. AI의 YAML 수정, 정책 자동 배포, 취약점 자동 수정과 실제 고객 연동은 범위에서 제외한다.

- **탐지:** Tetragon이 정책에 맞는 활동을 관찰해 이벤트를 만든다. 우리 서비스는 해당 이벤트를 경고로 표시한다.
- **대응:** 사전에 적용한 Tetragon 정책이 지원되는 조건에서 설정된 동작을 수행한다. SaaS나 AI가 실시간으로 차단 여부를 결정하지 않는다.
- **분석:** AI는 이벤트의 의미와 추가 확인 사항을 설명한다. 공격이나 취약점을 확정하지 않는다.

## 구조

```text
클라이언트: 로컬 Linux 환경
┌────────────────────────────────────────────────────────────┐
│ 시연용 서버 컨테이너                                        │
│       │ 프로세스·파일·네트워크 활동                         │
│       ▼                                                    │
│ Tetragon                                                   │
│ ├─ 커널: eBPF 프로그램이 정책에 따라 활동 관찰·대응         │
│ └─ 사용자 영역: Agent가 이벤트 제공                         │
│       │ JSON 이벤트                                        │
│       ▼                                                    │
│ 이벤트 전송 모듈 ───── HTTP ────────────────────┐          │
└─────────────────────────────────────────────────┼──────────┘
                                                  ▼
우리 서비스: 로컬 실행
┌────────────────────────────────────────────────────────────┐
│ 백엔드: 수신·저장·경고 분류·조회 / AI 분석 요청            │──→ 외부 AI API
│       │                                                    │
│ 대시보드: 이벤트 목록·상세·화면 알림·AI 조사 안내          │
└────────────────────────────────────────────────────────────┘
```

대응은 클라이언트에 이미 적용된 정책에 따라 이뤄진다. SaaS 또는 AI의 응답을 기다렸다가 차단하는 구조가 아니다. Tetragon이 생성하는 이벤트와 사용할 수 있는 대응 동작은 선택한 정책·버전·환경에 따라 확인한다.

macOS에서 Docker Desktop을 사용하면 관찰 대상은 macOS가 아니라 Docker의 Linux VM 안의 활동이다. Tetragon의 권한·커널 지원·정책 적용과 컨테이너 이벤트 수집이 해당 환경에서 동작하는지 먼저 확인한다. 컨테이너의 `localhost`는 그 컨테이너 자신이므로 백엔드 주소도 실제 배치에 맞게 정한다.

## 컴포넌트

### 1. 시연용 서버

간단한 서버 컨테이너와 시연용 파일을 준비한다. 선택한 정책의 조건에 맞는 활동을 반복 실행해 탐지와 대응을 확인한다. 실제 취약점이나 공격 기능은 필요하지 않다. 시연 대상은 다른 작업과 분리한다.

### 2. Tetragon과 미리 준비한 정책

Tetragon Agent가 정책과 eBPF 프로그램을 관리하고 이벤트를 제공한다. eBPF 프로그램은 커널의 설정된 지점에서 활동을 관찰하고 정책에 정의된 지원 가능한 대응을 수행한다.

- **관찰 정책:** 시연할 프로세스 실행 또는 파일 접근의 이벤트를 생성한다.
- **대응 정책:** 시연할 조건 하나에 대해 Tetragon이 지원하는 대응 동작을 수행한다. 정책은 사람이 미리 준비하고 검증한다.
- **정책 범위:** 구체적인 대상·조건·동작은 시연 환경과 지원 여부를 확인한 뒤 확정한다. 세 가지 활동 유형을 모두 구현하는 것은 단일 시연 완성 이후로 둔다.

프로세스에 `SIGKILL`을 보내는 것과 시도한 작업을 거부하는 것은 다르다. 종료만으로 파일 쓰기 같은 작업이 수행되지 않았다고 보장할 수 없다. 지원되는 훅에서 반환값을 변경해 거부하는 방식도 있으나, 커널·훅·Tetragon 버전의 지원 여부를 확인해야 한다. **검증한 결과에 맞춰 ‘프로세스 종료’ 또는 ‘작업 거부’라고 표현한다.**

### 3. 이벤트 전송 모듈

Tetragon의 JSON 이벤트를 읽고 백엔드에 HTTP로 전송한다. 시연에 필요한 이벤트를 선택하고 원본을 함께 전달한다. 초기에는 전송 실패를 로그로 표시한다. 재전송과 유실 복구는 필수 범위가 아니다.

Tetragon은 JSON 파일 출력과 gRPC 이벤트 스트림을 제공한다. 시연 환경에서 먼저 동작하는 방식을 선택하고 파일 접근 권한·로그 순환 또는 스트림 연결을 확인한다.

### 4. 백엔드와 알림

하나의 애플리케이션에서 이벤트 수신·정리·저장·조회와 AI 요청을 처리한다. 시연용 조건에 맞는 이벤트를 `확인 필요`로 표시한다. 정책에 일치했다는 사실과 공격 판정은 구분한다.

알림은 우선 **대시보드 내 새 경고 표시**로 구현한다. 주기적 조회에서 새 경고를 발견해 화면에 표시하므로 사용자가 화면을 열어둔 동안에만 확인할 수 있다. 이메일·Slack·푸시는 추가 범위다.

메모리 저장을 기본으로 하며 서버 재시작 시 이벤트가 사라진다. 보존이 필요하면 SQLite를 선택한다. 기술 스택과 저장 방식의 최종 선택은 미정이다.

### 5. 대시보드와 AI

한 화면에 이벤트 목록과 상세, 확인 가능한 대응 정보, 새 경고 표시와 AI 조사 안내를 보여준다.

```text
새 경고: demo-server에서 정책에 해당하는 활동 관찰

시간       대상 서버     유형          내용                 상태
10:30:12   demo-server  파일 접근     시연용 파일 접근      확인 필요

상세: 시각 · 프로세스 · 대상 · 정책명 · 관찰된 대응 정보 · 원본
[AI 조사 안내 받기]
```

정책에 대응이 설정된 사실과 실제 대응 결과를 구분한다. 이벤트만으로 결과를 확인할 수 없다면 `확인 불가`로 표시하고 별도의 실제 동작 확인 결과를 시연에서 설명한다.

AI는 선택한 이벤트와 사용자가 입력한 서버 역할을 바탕으로 관찰된 사실, 가능한 해석, 정상 작업 가능성, 추가 확인 사항을 구분해 설명한다. 공격을 확정하거나 정책을 변경하지 않는다. AI 호출 실패 시에도 이벤트 목록과 상세를 볼 수 있다. API 키는 환경변수로 제공한다.

## 데이터와 API

실제 Tetragon JSON 구조를 확인한 뒤 필요한 항목을 추출한다. 다음은 내부 계약 초안이며 Tetragon의 원본 형식이 아니다.

| 항목 | 용도 |
|---|---|
| `id`, `receivedAt` | 백엔드가 부여하는 식별자와 수신 시각 |
| `occurredAt`, `instanceId` | 이벤트 발생 시각과 시연 인스턴스 식별자 |
| `eventType`, `policyName` | 실제 확인된 이벤트 유형과 정책명. 없는 값은 미상 |
| `process`, `target` | 이벤트에 포함된 프로세스와 파일·네트워크 대상 |
| `action`, `outcome` | 이벤트나 별도 확인으로 확인된 대응 동작·결과. 알 수 없으면 미상 |
| `status`, `reason` | 우리 서비스의 시연용 경고 분류와 이유 |
| `raw` | 원본 확인과 문제 진단용 이벤트 |

| API | 역할 |
|---|---|
| `POST /api/events` | 전송 모듈의 이벤트 수신 |
| `GET /api/events` | 최근 이벤트 목록 조회 |
| `GET /api/events/{id}` | 이벤트 상세 조회 |
| `POST /api/events/{id}/analysis` | 선택한 이벤트의 AI 조사 안내 생성 |

AI에 전달하는 필드와 외부 전송 사실을 사용자에게 표시한다. 이벤트에 포함되지 않은 정보는 추측하지 않는다.

## 시연과 확인

1. Tetragon을 실행하고 선택한 시연 행동의 이벤트가 실제로 발생하는지 확인한다.
2. 미리 준비한 대응 정책을 적용하고 행동을 다시 실행한다.
3. Tetragon 이벤트와 함께 프로세스 상태 또는 작업 결과를 별도로 확인한다. 파일 쓰기 거부가 목적이라면 파일 내용도 확인한다.
4. 실제 이벤트가 전송 모듈을 통해 대시보드에 표시되고 화면 알림이 발생하는지 확인한다.
5. 선택한 이벤트에 대한 AI 조사 안내를 확인한다.

완료 기준은 **실제 이벤트가 화면에 나타나고, 미리 정한 대응의 결과가 독립적으로 확인되며, 화면 알림과 AI 조사 안내를 볼 수 있는 것**이다. 이벤트만으로 차단 성공을 추론하거나 검증하지 않은 우회 방지 효과를 주장하지 않는다.

## 개발 분담과 순서

1. **Tetragon·시연 환경:** Linux에서 Tetragon 실행, 단일 정책 적용, 이벤트와 실제 대응 결과 확인. 실제 JSON과 재현 방법을 공유한다.
2. **전송·백엔드:** JSON 이벤트 수신·정리·저장·조회 API 구현. 실제 JSON이 나오기 전에는 예시로 연결하고 이후 실제 출력으로 확인한다.
3. **대시보드·AI:** 목록·상세·화면 알림을 예시 데이터로 준비하고, API와 AI 조사 안내를 연결한다.

먼저 Tetragon의 정책과 실제 동작을 검증한 뒤 이벤트를 화면까지 연결하고, 마지막에 AI를 붙인다. 세 활동 유형의 확장은 단일 흐름이 완성된 이후에 결정한다.

## 남은 결정

시연할 구체적인 행동과 대응 목표(프로세스 종료 또는 작업 거부), Tetragon 버전·Linux 실행 환경, 이벤트 추출 방식, 백엔드·프론트엔드 기술 스택, AI 제공자와 외부 전송 필드. 외부 알림과 실제 고객별 정책 관리는 추후 별도로 결정한다.
